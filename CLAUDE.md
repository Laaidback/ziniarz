# ZINIARZ

Aplikacja webowa do składania zinów: broszura zszywana z kartek A5 (wyciętych z A4) złożonych na pół (każda kartka = 4 strony A6), druk dwustronny na domowej drukarce ze spadami i liniami cięcia. Spec: `docs/superpowers/specs/2026-10-14-ziniarz-design.md` (przejście na A6: `2026-10-15-ziniarz-a6-design.md`; okładka w całości: `2026-10-15-ziniarz-okladka-design.md`). Plany: `docs/superpowers/plans/`.

Użytkowniczka nie jest programistką: pisze po polsku i opisuje efekt, a nie implementację. Odpowiadaj po polsku. Kod, komentarze i commity pisz po angielsku. Interfejs i komunikaty błędów po polsku.

## Szybki start

```bash
npm install
npx playwright install chromium
npm test
npm run test:e2e
npm run dev
```

- `npm run test:unit`: czysta logika w Node. `npm run test:browser`: render, fonty, PDF, WebGL i komponenty React w Chromium (Vitest browser mode, okno 1280×900).
- `npm run test:e2e`: Playwright (`e2e/`, `playwright.config.ts`) na zbudowanej apce (`vite build` + `vite preview` na porcie 4173): nowy zin 5 kartek, zdjęcie, napis, PDF do druku ma 10 stron A4 poziomo; podgląd 3D. Nie wchodzi do `npm test`.
- `test-output/`: próbne arkusze PNG i PDF z `src/print/samples.browser.test.ts` do obejrzenia.
- `npm run test:update-references`: świadome odświeżenie wzorców renderu (`src/print/__reference__/`), zob. „Wzorce renderu” niżej.
- `npm run check:dist` (po `npm run build`): sprawdza, że zbudowana strona nie ma adresów od korzenia serwera (`/assets/...`) i że wszystkie pliki, do których się odwołuje, są w `dist/`. Bez tego strona pod GitHub Pages (`/<repo>/`) by się nie wczytała. Logika w `scripts/checkDist.mjs`, testy w `src/build/checkDist.test.ts`.
- `.claude/launch.json`: serwer deweloperski dla podglądu w Claude Code (`ziniarz-dev`, port 5199).
- `vite.config.ts` wymienia biblioteki w `optimizeDeps.include`, żeby testy w przeglądarce nie przeładowywały się w trakcie przebiegu. Każdą nową bibliotekę używaną w testach przeglądarkowych dopisz tam też.

## Publikacja

- Hosting: GitHub Pages, adres `https://<user>.github.io/<repo>/`. `.github/workflows/deploy.yml` po każdym pushu do `main` (i ręcznie: Actions → Run workflow) uruchamia po kolei: `npm run typecheck`, `npm test`, `npm run test:e2e` (tylko gdy skrypt istnieje), `npm run build`, `npm run check:dist`, a potem wysyła `dist/` na Pages. Czerwony test blokuje publikację. CI używa Node 24 i akcji `checkout@v7`, `setup-node@v7`, `configure-pages@v6`, `upload-pages-artifact@v5`, `deploy-pages@v5`.
- Wymaga w ustawieniach repo *Settings → Pages → Source: GitHub Actions*. Chromium do testów instaluje workflow (`npx playwright install --with-deps chromium`).
- **Repo, `remote` i `push` zostały celowo niewykonane:** to publikacja publiczna i decyzja właścicielki. Instrukcja jest w `README.md`. Nie zakładaj repo ani nie pushuj bez jej polecenia.
- Strona działa pod podadresem, więc `base` w `vite.config.ts` zostaje `'./'`, a adresy ekranów są po haszu (`#/zin/<id>`), bez routingu po stronie serwera i bez `404.html`. **Nie używaj adresów zaczynających się od `/`** (np. `/fonts/x.woff2`, `fetch('/api')`, `<img src="/logo.png">`). Zasoby importuj w kodzie (`import url from '...?url'`) albo przez `new URL('./x', import.meta.url)`; `npm run check:dist` to wyłapie.
- Ziny są w IndexedDB przeglądarki, osobno dla każdego adresu (`localhost` i adres na GitHub Pages to dwa różne magazyny): przenosi się je plikami `.zin`.
- Nowe wersje akcji w workflow podnoś parami (`upload-pages-artifact` razem z `deploy-pages`).

## Zasady i niezmienniki

- **Jednostki:** wszystko w milimetrach na wydrukowanej stronie A6 (105×148). Rozkładówka: x 0…210, grzbiet x = 105, spad 3 mm poza nią. Rozmiary bierz ze stałych `PAGE_WIDTH`, `PAGE_HEIGHT`, `SPREAD_WIDTH`, `BLEED` (`geometry.ts`). Rozmiar napisu (`size`) to punkty na wydruku. Domyślne marginesy 12 / 7 / 14 / 11 mm (zewnętrzny, przy grzbiecie, górny, dolny), nowy napis 9 pt.
- **Rozkładówka 0 to cała okładka od zewnątrz:** lewa strona `P` (tył), prawa `1` (przód). Rozkładówka `i ≥ 1` ma strony `2i` (lewa) i `2i + 1` (prawa); rozkładówek jest `2 · sheets`, każda ma dwie strony. Numerację znają tylko `pageAt`, `slotOfPage` (biorą liczbę kartek) i `sideOfPage` (`geometry.ts`). Element należy do rozkładówki i może leżeć przez grzbiet, także na okładce.
- **Jeden rysownik.** Edytor, miniatury, PDF i 3D rysują przez `buildSpreadGroup`. Nie twórz osobnej ścieżki rysowania. Tekst rysuje i mierzy tylko `createTextShape` (`Konva.Text`); wysokość ramki napisu liczy `measureTextHeight`, a pole edycji tekstu bierze rozmiary z `textStyleMm`.
- **Płótno edytora to zwykła Konva** (`EditorStage`), nie react-konva: rysunek rozkładówki pochodzi z rysownika, klasa dokłada tylko prowadnice, zaznaczenie, przyciąganie i obsługę myszy. Transformer działa na niewidocznym prostokącie (`proxy`) w warstwie bez skali.
- **Stan edytora:** zmiany zina tylko przez akcje sklepu (`edit`, `updateElement`…), każda to krok cofania (do 100). Zmiany z tym samym kluczem (pisanie, suwaki, pola liczb, przesuwanie zdjęcia w kadrze) łączą się w jeden krok, a **na końcu każdej interakcji (puszczenie myszy, blur, Enter) wołaj `endMerge()`**; łączenie kończy też `select`, `clickPage`, `setSpread` i `setMode`. Zmiana, która nic nie zmienia, zwraca ten sam zin i nie robi kroku cofania. Cofnięcie i ponowienie ponownie mierzą wysokości napisów i przełączają na rozkładówkę ze zmianą. Dodanie i usunięcie kartki zostawia podgląd na tej samej rozkładówce. Zaznaczenie, rozkładówka i tryb nie są w historii. Klik w element na płótnie zaznacza go i ustawia `activePage` na istniejącą stronę pod kursorem (`select(id, page)`), więc nowy napis lub zdjęcie trafia na klikniętą stronę, także przy zdjęciu przez całą rozkładówkę. Sklep nie importuje Konvy: pomiar tekstu i rozmiar zdjęcia dostaje w `EditorDeps`. Po „± kartka” kliknięta strona zostaje po tej samej stronie rozkładówki (`activePage` przez `pageAt`), więc kliknięty tył okładki zostaje tyłem.
- **`EditorStage.update` przebudowuje węzły elementów tylko, gdy zmieniła się treść** (zin, rozkładówka, zdjęcia, `contentVersion` z wersji zdjęć i fontów, tryb, napis w edycji). Samo zaznaczenie ich nie rusza: Konva wysyła `dblclick` tylko wtedy, gdy oba kliknięcia trafią w ten sam węzeł, a pierwsze kliknięcie zaznacza. Aktualizacje w trakcie przeciągania czekają do `finishGesture()`, które rysuje je po puszczeniu myszy. Test pilnuje obu rzeczy.
- **Selektory Zustand** zwracają wartości stałe (pole stanu albo element), nigdy nowy obiekt, bo React wpada w pętlę.
- **Notatnik:** `Zine.notes` (domyślnie `''`) to tekst notatnika w małym podzbiorze HTML: tekst, `<b>`, `<mark>`, `<br>`, `<div>`, `<p>`, bez atrybutów. Pilnuje tego `sanitizeNotes` (`src/model/notesHtml.ts`, na napisach, bez DOM) w `parseZine` (plik `.zin` od kogoś nie wniesie własnego HTML-a) i w `setNotes`; zwykły tekst wychodzi z niego ucieczką znaków, a łamania linii zostają (pole ma `white-space: pre-wrap`). `sanitizeNotes` czyta tekst jednym przejściem (bez wyrażeń regularnych, które mogłyby się cofać: wrogi plik `.zin` nie może zawiesić listy zinów; test czasu na 100 KB), tag bez `>` zostawia resztę jako tekst, zamknięcie usuwanego elementu (`</script` itp.) szuka bez względu na wielkość liter w oryginalnym tekście, a każdą sekcję tnie do `MAX_NOTES_LENGTH` (200 000 znaków). `setNotes` zmienia zina **bez kroku cofania** (pole ma własne cofanie przeglądarki), a autozapis widzi to jak każdą zmianę. **Cofnięcie i ponowienie projektu nigdy nie zmieniają notatek** (`travel` przenosi bieżące notatki do przywracanego stanu), a każda zmiana projektu startuje od bieżącego zina, więc stare notatki z historii nie wracają. Pole to `contentEditable` niesterowane przez Reacta (wypełniane raz przy otwarciu): pogrubienie przez `execCommand('bold')`, marker ręcznie przez `<mark>` (`toggleMark`, nie `hiliteColor`, bo to style w linii); marker zmienia DOM poza `execCommand`, więc ⌘Z przeglądarki w notatniku nie cofa samego zaznaczenia markerem (i może pomieszać wcześniejsze kroki) — znane ograniczenie, odznacza się je tym samym przyciskiem, wklejanie i upuszczanie tylko jako zwykły tekst. „Wstaw zaznaczenie jako napis” wstawia zwykły tekst zaznaczenia przez `insertTextFrame` (zaznaczony, bez trybu pisania, jeden krok cofania). Skróty edytora nie działają, gdy fokus jest w notatniku (`isTypingTarget`). Widoczność kolumny (przycisk „Notatnik”, `aria-pressed`, i „Schowaj” w nagłówku notatnika) jest w `localStorage` (`ziniarz.showNotes`, w `try/catch`), domyślnie widoczna. **Notatnik dzieli się na rozkładówki:** `Zine.spreadNotes` (domyślnie `{}`, bez zmiany `FORMAT_VERSION`) to notatki poszczególnych rozkładówek po `Spread.id`, więc idą za swoją rozkładówką przy „± kartka”; `Zine.notes` to sekcja „Ogólne”. `parseZine` czyści każdą wartość `sanitizeNotes`, odrzuca klucze rozkładówek, których nie ma, i puste notatki (rozkładówka bez notatek nie ma klucza). `setSpreadNote(id, html)` działa jak `setNotes` (bez kroku cofania). Cofnięcie i ponowienie przenoszą bieżące notatki rozkładówek, które zostają; rozkładówki, które wracają (cofnięte „− kartka”), wracają ze swoimi notatkami z migawki (`withCurrentNotes` w `store.ts`). `removeSheet` usuwa notatki usuwanych rozkładówek, a „− kartka” traktuje je jak treść: pyta najpierw i mówi o „notatkach w notatniku” (`removalHasNotes`, `removalMessage`). „Powiel” daje rozkładówkom nowe id i przenosi pod nie notatki (`copyOfZine`); plik `.zin` zachowuje id rozkładówek. Notatnik pokazuje „Całość” (sekcja „Ogólne”, potem sekcja na każdą rozkładówkę z nagłówkiem `spreadName`, jeden przewijany dokument) albo „Ta rozkładówka” (tylko sekcja otwartej rozkładówki, idzie za miniaturami i PageUp/PageDown); wybór w `localStorage` (`ziniarz.notesView`, w `try/catch`), domyślnie „Całość”. Każda sekcja to osobne pole `contentEditable` (pasek B / Zaznaczenie i skróty działają na sekcji z zaznaczeniem). W „Całości” sekcja otwartej rozkładówki jest wyróżniona („teraz”) i płynnie przewija się do widoku po zmianie rozkładówki, bez zabierania fokusu i nie wtedy, gdy fokus jest w innej sekcji; klik w nagłówek sekcji otwiera tę rozkładówkę. Pusta sekcja pokazuje jasną podpowiedź „Notatki do: Strony 4–5”. „Wstaw zaznaczenie jako napis” z sekcji innej rozkładówki najpierw przełącza edytor na nią, więc napis trafia tam, do czego był pisany (z „Ogólne”: na otwartą rozkładówkę). Pola sekcji mają nazwy „Notatki: Ogólne”, „Notatki: Strony 2–3”. Rysownik, druk i 3D notatek nie czytają; płótno edytora i miniatury nie rysują się od nowa, gdy zmieniają się tylko notatki (`drawnChanged` w `EditorStage`).
- **Szerokość kolumn bocznych:** lista stron (uchwyt na prawej krawędzi, 140…360 px, domyślnie 180, `ziniarz.spreadsWidth`), ustawienia (lewa krawędź, 240…480 px, 300, `ziniarz.settingsWidth`) i notatnik (lewa krawędź, 220…min(720 px, 55 % okna), 280, `ziniarz.notesWidth`) mają ten sam uchwyt `ColumnResizer.tsx` (`role="separator"`; przeciąganie myszą z przechwyceniem wskaźnika, strzałki co 20 px, z Shift 60 px, w stronę zgodną z krawędzią; dwuklik = domyślna; szara nakładka, złota na notatniku) i te same zasady w `columnWidth.ts` (`useColumnWidths`, czysta `fitColumnWidths`): szerokość w `localStorage` (try/catch), dopasowywana do okna przy wczytaniu i zmianie jego rozmiaru; płótno zawsze zostaje przy co najmniej 360 px (gdy kolumny się nie mieszczą, najpierw ustępuje notatnik, potem ustawienia, potem lista stron, nigdy poniżej minimum; wybrana szerokość zostaje zapamiętana). Szerokości idą do CSS jako zmienne `--spreads-width`, `--settings-width`, `--notes-width` na `.editor`; płótno samo się dopasowuje (`ResizeObserver`). Miniatury rozkładówek rosną razem z kolumną: `thumbnailPxPerMm` dobiera ich rozdzielczość skokami co 0,4 px/mm (z gęstością pikseli ekranu). Zawartość przewijana kolumn jest w `.column-scroll`, żeby uchwyt mógł wystawać poza krawędź.
- **Spad tylko na zewnętrznych krawędziach strony;** przy grzbiecie strona kończy się równo (`pageRect`).
- **Prowadnice edytora** (`buildGuidesGroup` w `src/render/guides.ts`, tylko gdy „Pokaż prowadnice”, nigdy w druku, miniaturach ani 3D) pokazują linię cięcia każdej strony (cienka szara ciągła, `guide-trim`), lekko zabarwiony spad poza nią (`guide-bleed-zone`) z czerwoną przerywaną krawędzią spadu, niebieskie przerywane marginesy i grzbiet. Marginesy liczą się od linii cięcia, nie od krawędzi spadu: dlatego przy równych marginesach odstęp czerwonej linii od niebieskiej jest na zewnętrznych bokach o 3 mm większy niż przy grzbiecie.
- **Impozycja:** kartka `k`: przód `P − 2k | 2k + 1`, tył `2k + 2 | P − 2k − 1`. PDF poziomy, tył pod „odwracanie po krótszej krawędzi”; „Obróć tyły o 180°” dla drukarek odwracających po dłuższej.
- **Druk 100%:** kartka A5 (dwie strony A6) ze spadem stoi na środku A4 poziomo w skali 1; spad i znaczniki zostawiają ponad 20 mm papieru do krawędzi (pilnuje test), więc nie ma marginesu drukarki ani skalowania. Ekran druku pokazuje „Strona po przycięciu: 105 × 148 mm” i przypomina o druku w rzeczywistym rozmiarze (100%).
- **Kartki:** dodawanie i usuwanie nigdy nie przesuwa okładek ani wewnętrznych stron okładek (poza wyjątkami 1 i 2 kartek opisanymi w specu). Kolory tła idą za stronami.
- **Kompatybilność danych:** nowe pole = wartość domyślna w `parseZine`. Zmiana znaczenia pola = nowa `FORMAT_VERSION` i migracja. Nowsza wersja pliku = czytelny błąd, nigdy częściowy zin. `FORMAT_VERSION` 3 = okładka w jednej rozkładówce; wersja 2 i starsze mają osobną ostatnią rozkładówkę z tyłem, którą `parseZine` łączy z rozkładówką 0 (`mergeCovers`, tył pod przodem, współrzędne bez zmian). Dane o złym kształcie (`mergeCovers` zwraca `null`) dają błąd uszkodzonego zina. `FORMAT_VERSION` 2 = strony A6; wersja 1 (albo brak wersji) to A5 i `parseZine` przelicza ją przez `migrateA5ToA6` (spad zostaje 3 mm, kadr zdjęć nie odsłania tła). Zapis zawsze z `parseZine`, więc przeliczony zin nigdy nie jest zapisany jako wersja 1. **Zin z bazy zawsze przechodzi przez `parseZine`** (lista zinów, otwieranie w edytorze).
- **Zdjęcia i fonty leżą w IndexedDB, nigdy w JSON-ie zina.** Sprzątanie (`pruneUnusedAssets`) tylko z listy zinów, nigdy w trakcie edycji, i dopiero po `whenSavesSettled()`, żeby świeżo dodane zdjęcie nie wyglądało na nieużywane. Font jest „używany”, gdy jest na liście `Zine.fonts`; pliki fontów bez rekordu rodziny też są sprzątane.
- **Kilka kart przeglądarki:** każdy ekran z otwartym zinem (edytor, druk, 3D; `holdOpenZineLock` w `EditorScreen` i `useZineView`) oraz wczytywanie pliku `.zin` trzyma Web Lock `ziniarz-open-zine` we współdzielonym trybie (`src/storage/zineLock.ts`). Lista zinów sprząta tylko przez `whenNoZineIsOpen` (blokada na wyłączność z `ifAvailable`): gdy inna karta ma zin otwarty, sprzątanie czeka do następnego razu. Bez `navigator.locks` sprząta jak dawniej. Testowe bazy mają własną nazwę blokady (`openZineLockName`), żeby równoległe pliki testów się nie blokowały.
- **Trwały magazyn:** `persistentStorage()` (`quota.ts`) pyta przeglądarkę raz na wczytanie strony (`App`). Gdy odmówi albo nie umie, lista zinów pokazuje stały, spokojny dopisek „Przeglądarka może kiedyś usunąć ziny. Zapisuj co jakiś czas pliki .zin.” (nie okienko). „Zajęte miejsce” lista czyta po każdej zmianie listy i jeszcze raz po 1,5 s i 5 s, bo przeglądarka aktualizuje tę liczbę z opóźnieniem.
- **Autozapis** 500 ms po zmianie, zapisy po kolei; wyjście z edytora albo z ekranu druku i ukrycie karty (`onPageHide` w `src/app/onPageHide.ts`: `pagehide` i `visibilitychange`) zapisują od razu. `updatedAt` ustawia zapis.
- **Fonty:** wbudowane rodziny mają id jak `fontFamilyId` (`inter`, `lora`…), domyślna `inter` (nowe napisy: zob. Ayuthaya niżej). Każdy styl to dwa pliki (latin i latin-ext z polskimi literami), przeglądarka pobiera je dopiero, gdy tekst ich potrzebuje; `ensureFontsReady` i `loadSpreadFonts` podają tekst, żeby pobrała właściwe. Nowy wbudowany font = wpis w `BUILTIN_FONTS` i pliki w `builtinFontFiles.ts` (test pilnuje zgodności). Własne fonty: rodzina z tabeli `name` (ID 1) i bitów OS/2 dla TTF/OTF, z nazwy pliku dla WOFF2. Poza pogrubieniem i kursywą waga (Light, SemiBold…) zostaje w nazwie rodziny („Lato Light”), żeby komplet wag nie nadpisywał Regular i Bold.
- **Ayuthaya (font z macOS):** licencja Apple nie pozwala go rozpowszechniać, więc **nigdy nie dodawaj jego plików do repo ani strony**. Aplikacja bierze kopię z komputera przez `local('Ayuthaya')` (`SYSTEM_FONTS` w `fontChoices.ts`, bez plików w `builtinFontFiles.ts`; test pilnuje, że ich nie ma). `detectSystemFonts()` (`systemFonts.ts`, wołane w `main.tsx`, `loadFontChoices` i `ensureFontsReady`) raz na wczytanie strony sprawdza, czy font jest (`FontFace.load()` i porównanie szerokości tekstu na canvasie), i rejestruje go jako `zf-ayuthaya`. Tylko Regular (pogrubienie i kursywa wyłączone). **Nowy napis** (`insertTextFrame`) dostaje `defaultFontFamilyId()`: `ayuthaya`, gdy font jest, inaczej `inter`. `createTextElement` i `parseZine` zostają przy `inter` (`DEFAULT_FONT_FAMILY`), żeby nie zmieniać starych zinów. Lista fontów pokazuje „Ayuthaya (z macOS)” tylko, gdy font jest; zin z Ayuthayą na komputerze bez niej pokazuje „Ayuthaya (brak na tym komputerze)” i rysuje w Inter (`konvaFontFamily`: `zf-ayuthaya, zf-inter, sans-serif`; `ensureFontsReady` ładuje wtedy pliki Inter). Plik `.zin` nie ma plików Ayuthayi. W testach przeglądarkowych Ayuthaya domyślnie „nie istnieje” (`src/test/browserSetup.ts`), test zmienia to przez `setSystemFontAvailability`.
- **Rodziny fontów są wspólne między zinami po id** (powielony zin, „Użyj fontu z innego zina”). Wgranie pliku do rodziny, którą ma też inny zin, najpierw robi kopię rodziny dla tego zina (nowe id, kopie plików; `importFontFiles` zwraca `replaced`), a `FontField` podmienia id na liście fontów i w napisach (`replaceFontFamilies`) w jednym kroku cofania. Nigdy nie zmieniaj w miejscu rodziny, której używa inny zin.
- **Wczytanie `.zin` tworzy nowy zin** (nowe id), nigdy nie nadpisuje istniejącego. Rodzina fontów, której id już jest w bazie, dostaje nowe id razem z plikami, a zin i napisy idą za nią.
- **Dodawanie zdjęć** idzie przez `usePhotoInsert().add` (przycisk i upuszczenie na płótno): pasek pokazuje „Dodawanie zdjęć k z N…”, a wyjście z edytora przerywa (`AbortSignal`) przed kolejnym plikiem i zamyka niepotrzebne bitmapy. Plik HEIC/HEIF, którego przeglądarka nie odczyta, daje osobny komunikat (zapisz jako JPG); Safari HEIC odczytuje, więc rozpoznajemy go dopiero po nieudanym dekodowaniu (`isHeicFile`).
- **Eksport rysuje arkusze po jednym** i zwalnia canvas (`releaseCanvas`); `drawToCanvas` wymusza `Konva.pixelRatio = 1`.
- Opcje druku zapisuje do `Zine.print` ekran druku (autozapis jak w edytorze), poza sklepem edytora i historią cofania.
- **Ekrany druku i 3D tylko oglądają zina:** otwierają go przez `openZineView` (czeka na `whenSavesSettled()`, potem `parseZine`, fonty, zdjęcia) i nie zmieniają jego treści.
- **Pobieranie PDF:** `runExport` buduje wszystkie pliki, zanim cokolwiek pobierze; błąd = komunikat `EXPORT_FAILED` z „Spróbuj jeszcze raz”, nic nie zostaje pobrane. Ekran druku dostaje `PdfExporter` (testy podają szybszy albo psujący się). Budowniczowie PDF (`buildSheetsPdf`, `buildPagesPdf`) biorą `AbortSignal` i przerywają przed kolejną stroną arkusza albo stroną zina; ekran druku przerywa eksport przy odmontowaniu (wyjście z ekranu), a przerwany eksport niczego już nie pobiera ani nie zgłasza. Eksport z kilkoma plikami (ręczny druk dwustronny) pokazuje po jednym przycisku pobierania na plik i nie pobiera nic sam, bo przeglądarka przepuszcza tylko pobranie wywołane kliknięciem.
- **Podgląd arkuszy** rysuje stronę arkusza dopiero, gdy wjedzie w widok (`IntersectionObserver`), po jednej (`createRenderQueue`), w rozdzielczości dopasowanej do szerokości na ekranie i gęstości pikseli (`previewDpi`: 48–200 dpi, skokami po 24; przy poszerzeniu okna rysuje ostrzej, przy zwężeniu nie rysuje od nowa). Tyły pokazuje zawsze nieobrócone (tak wychodzą z drukarki).
- **Podział kodu:** edytor i ekran druku (z pdf-lib) ładują się dopiero przy pierwszym wejściu: `React.lazy` w `App.tsx`, owinięte w `ScreenBoundary` („Wczytywanie…”, a gdy kod się nie pobierze: komunikat i powrót do listy). Nie importuj `EditorScreen`, `PrintScreen` ani `pdf-lib` statycznie z listy zinów i wspólnego kodu, bo wrócą do głównego pakietu (sprawdź wynik `npm run build`).
- **3D:** three.js ładuje się tylko przez `import('./scene')` w `Preview3dScreen`; nie importuj `three` nigdzie poza `src/preview3d/scene.ts`, bo trafi do głównego pakietu. Kartkowanie, kąty, grubość papieru, klik i klawisze liczą `book.ts` i `view.ts` (testy w Node); `ZineScene` tylko rysuje i rysuje klatkę na żądanie (`invalidate`), nie w pętli. Tekstury stron z `renderPage` bez spadu, 1024 px wysokości, liczone w tle po otwarciu; canvas zwalniany po wysłaniu do GPU. **`scene.dispose()` woła `renderer.forceContextLoss()`**, żeby wyjście z ekranu zwalniało kontekst WebGL (przeglądarka ma ich ograniczoną liczbę). **Po przywróceniu kontekstu** (`webglcontextrestored`, opcja `onContextRestored`) ekran rysuje tekstury stron od nowa, bo GPU je zgubił. Podpis w 3D (`spreadCaption`) liczy się z pozycji czytelnika (zamknięty z przodu „Okładka”, z tyłu „Tył”), nie z rozkładówek edytora.
- **WebGL w testach:** Chromium bez ekranu rysuje przez SwiftShader; flagi `--use-angle=swiftshader --enable-unsafe-swiftshader` są w `vite.config.ts` i `playwright.config.ts`. Obraz WebGL czytaj zaraz po `renderFrame` (później bufor jest pusty).
- **Nazwy plików** nie mogą różnić się tylko wielkością liter (macOS jej nie rozróżnia): stąd `notices.ts` i `NoticeList.tsx`, `spreadLabels.ts` i `SpreadList.tsx`.
- **Dostępne nazwy:** przyciski i pola bez własnego tekstu dostają `aria-label` (miniatury rozkładówek: `spreadName` — „Okładka”, „Strony 2–3”); pole wyboru w etykiecie-opakowaniu dostaje też `aria-label`, bo niektóre narzędzia nie łączą go z etykietą.
- **Wzorce renderu:** `src/print/reference.browser.test.ts` rysuje oba boki każdej kartki przykładowego zina (`src/test/sampleZine.ts`: 3 kartki w milimetrach A6, napisy w Inter, zdjęcie generowane w teście, w tym pas zdjęcia owijający okładkę przez grzbiet) w 72 dpi ze spadem i znacznikami i porównuje je z PNG w `src/print/__reference__/` (w repo, nie w `.gitignore`). Piksel się różni, gdy kolor wychodzi poza zakres kolorów sąsiednich pikseli wzorca (±24 na kanał), w którąkolwiek stronę; to wchłania wygładzanie krawędzi i przesunięcia o piksel. Test pada powyżej 0,5 % różnych pikseli i zapisuje `test-output/reference/<arkusz>.actual.png` oraz `.diff.png` (różnice na czerwono). Próg jest zgrubny, z zapasem na inne fonty systemu w CI (Linux, wzorce z macOS): łapie zgubione zdjęcie, złą kolejność stron, zły kolor, przesunięty układ; drobiazgi pilnują testy jednostkowe (np. szew przy grzbiecie w `sheetSide.browser.test.ts`). **Odświeżanie tylko świadomie:** po zamierzonej zmianie rysowania albo przykładowego zina `npm run test:update-references` (ustawia `UPDATE_REFERENCES=1`, które `vite.config.ts` podaje testom przez `test.provide`), obejrzyj nowe PNG (zdjęcie przez grzbiet bez białego paska, znaczniki w rogach) i zacommituj je razem ze zmianą. **W CI porównanie jest tylko informacyjne:** gdy ustawione jest `CI` (GitHub je ustawia), `npm test` pomija test wzorców (`vite.config.ts` podaje to testom jako `skipReferences`), chyba że `REFERENCE_STRICT=1`. Workflow uruchamia go osobno w kroku „Render references (informational)” z `continue-on-error: true`, więc rozbieżność nie blokuje wdrożenia, a pliki z `test-output/reference/` (`.actual.png`, `.diff.png`) trafiają do artefaktu „roznice-renderu”. Lokalnie porównanie jest ścisłe. Nigdy nie odświeżaj wzorców, żeby uciszyć niezrozumiany błąd.
- **Kolumna „Ustawienia”** (panel zina, strony i zaznaczonego elementu, `PropertiesPanel`) jest **domyślnie schowana**, a płótno dostaje jej miejsce. Pokazuje ją przycisk „Ustawienia” u góry (`aria-pressed`), chowa on albo „Schowaj” w jej nagłówku (`aria-label` „Schowaj ustawienia”).
